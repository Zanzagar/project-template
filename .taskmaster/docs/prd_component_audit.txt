# Component Audit PRD — ECC v1.8.0 + Superpowers v5 Alignment

## Overview

Systematic comparison of every component in our project template against its equivalent in Everything Claude Code (ECC) v1.8.0 and Superpowers v5.0. The goal is to adopt upstream implementations where they are equal or better, and only retain our custom implementations where we have a genuine, documented improvement or philosophical divergence.

This audit MUST complete before any further v2.5.0 feature implementation. Many v2.5.0 tasks may become "adopt ECC's version" rather than build-from-scratch.

## Context

### The Problem

During v2.5.0 Task 1 implementation, we discovered we were writing inferior from-scratch code when a proven upstream implementation existed. ECC's `run-with-flags` architecture was superior in 4/6 dimensions to our hand-written `hook-profiles.js`. This pattern likely repeats across the entire template.

### The Principle

> At the component level, ECC and Superpowers will almost always implement things better than we can. Our value is in workflow integration, enforcement, and adaptation — not reimplementation.

### Decision Framework

For every component, assign one verdict:

| Verdict | Criteria | Action |
|---------|----------|--------|
| **Adopt** | Their version is better or equivalent in every way | Copy + adapt (env vars, paths, naming) |
| **Adapt** | Their skeleton is better but we have genuine improvements to merge | Start from theirs, merge our improvements |
| **Keep** | Ours is philosophically better for our workflow or genuinely superior | Document why explicitly |
| **New** | We have something they don't | Keep and document as our contribution |
| **Skip** | They have something we don't need | Document why skipped |

**Burden of proof is on "Keep"** — if you can't articulate a specific technical reason ours is better, the verdict is Adopt.

### Upstream Provenance Tracking

Every adopted/adapted file gets:
1. A header comment noting source repo, source path, and commit SHA
2. An entry in `.claude/upstream-manifest.json` with adaptations documented
3. This enables future incremental sync when upstream improves

## Architecture

### Audit Workflow Per Category

```
1. INVENTORY    → List all files in both repos for this category
2. MAP          → Identify overlapping components (same purpose, different implementation)
3. FETCH        → Download all ECC equivalents via gh api
4. COMPARE      → Side-by-side analysis: architecture, features, quality, performance
5. DECIDE       → Assign verdict (Adopt/Adapt/Keep/New/Skip) with explicit reasoning
6. EXECUTE      → Implement decisions: copy, adapt, or document
7. TEST         → Verify adapted code passes existing + ECC-derived tests
8. MANIFEST     → Update upstream-manifest.json with provenance
```

### Output Artifacts

| Artifact | Path | Purpose |
|----------|------|---------|
| Decision matrices | `docs/audit/category-decisions.md` | Per-category verdicts with reasoning |
| Upstream manifest | `.claude/upstream-manifest.json` | Provenance tracking for future sync |
| Audit summary | `docs/audit/AUDIT_SUMMARY.md` | Overall findings, patterns, recommendations |
| Sync script | `scripts/check-upstream.sh` | Future: detect upstream changes since last sync |

## Technology Stack

- **Comparison tooling**: `gh api` for fetching, `diff` for comparison, markdown for decision matrices
- **Adopted code**: Node.js (ECC's hook infrastructure), bash (where ECC uses bash)
- **Testing**: Node.js built-in test runner, bash test scripts
- **Provenance**: JSON manifest + shell script for upstream diff

## Technical Constraints

- ECC repo: `affaan-m/everything-claude-code` — use `gh api` (raw URLs 404)
- ECC skills are directories (`skills/<name>/SKILL.md`), commands are flat (`commands/<name>.md`)
- Our hooks are bash, ECC's are Node.js — adopt Node.js for new hooks, keep bash for existing
- Superpowers is a plugin (separate install), not a repo to fetch from — compare against installed version at `~/.claude/plugins/cache/superpowers-marketplace/superpowers/5.0.2/`
- Context budget: each phase should be one session to avoid context degradation
- `gh api` rate limits: 60 requests/hour unauthenticated, 5000/hour with token

## Success Criteria

1. Every template component has a documented verdict (Adopt/Adapt/Keep/New/Skip)
2. All Adopt/Adapt verdicts are executed with tests passing
3. Upstream manifest covers every adopted file with source SHA and adaptations
4. v2.5.0 task list is updated to reflect audit findings
5. `scripts/check-upstream.sh` can detect upstream changes for adopted files
