IMPORTANT: Each subtask you generate MUST include ALL of the following sections in its description field. This is not optional — every section must be present and specific, not generic.

## Required Subtask Description Structure

### 1. ACCEPTANCE CRITERIA (checkbox format)
Write 3-7 checkbox acceptance criteria. Each criterion MUST be specific and measurable:
- For API tasks: include exact HTTP methods, status codes, and response body shapes (e.g., "POST /api/v1/auth/verify-email returns 200 with {message: ...}")
- For data tasks: include exact field names, types, and enum values (e.g., "sets user.email_verified = True")
- For UI tasks: include exact user interactions, component states, and accessibility requirements
- For infrastructure tasks: include exact config keys, service names, and validation commands
- Include time thresholds where relevant (e.g., "token expires in 24 hours", "response < 200ms")
- Include edge cases with specific error codes (e.g., "expired token returns 400 with descriptive error")
- NEVER write generic criteria like "works correctly" or "handles errors properly"

Format:
- [ ] [Specific, measurable criterion with concrete values]

### 2. SCOPE
State explicitly what is IN scope and OUT of scope for this subtask:
- In Scope: [specific components, endpoints, files, or behaviors this subtask covers]
- Out of Scope: [related work explicitly excluded — reference sibling subtasks by name when applicable]

### 3. BUSINESS CONTEXT
One sentence explaining WHY this subtask matters to the product or user. Not what it does, but why it exists.

### 4. CODE PATTERNS TO FOLLOW
Reference existing implementations in the codebase that this subtask should mirror:
- Name specific functions, classes, or files as templates
- Specify the architectural pattern to follow (e.g., "service layer isolation: logic in auth_service.py, not route handler")
- If no existing patterns exist, state the convention to establish
- Only reference files you are confident exist — do not guess at paths

### 5. TECHNICAL CONSTRAINTS
List hard constraints that narrow implementation choices:
- Required libraries or services to use (and which NOT to use)
- Performance requirements (response time, throughput)
- Security requirements (auth, validation, encryption)
- Compatibility requirements (existing schema, API contracts)

## Quality Rules
- Every field name, endpoint, status code, or threshold mentioned must be specific — never placeholder or generic
- If the parent task references a PRD, use PRD-level specificity in the criteria
- Subtasks should be independently implementable — each one produces a working, testable increment
- Prefer fewer, richer subtasks over many thin ones
- When unsure about file paths, describe the module/component instead of guessing a path
