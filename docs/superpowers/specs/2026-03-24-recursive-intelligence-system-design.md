# Design Doc: Recursive Cross-Project Intelligence System

**Date:** 2026-03-24
**Status:** Draft — open for iteration
**Author:** Corey Hoydic + Claude
**Scope:** Architecture for an autonomous, recursive intelligence system that operates across all projects, using an Obsidian vault as the central knowledge store.

---

## 1. Vision

A system that acts as a continuously-improving brain across all projects and research. It operates autonomously overnight, analyzing each project deeply, finding cross-project patterns and contradictions, connecting research to implementation, and producing investigated recommendations — not raw suggestions — by morning. The system learns from feedback, converges on high-quality insights through recursive self-critique, and evolves its understanding over weeks and months.

The system is not a notification engine. It is a research partner that works while you sleep.

---

## 2. Core Principles

### 2.1 Recursion Over Pipeline

The system is not a pipeline (ingest → analyze → output). It is a recursive loop where:
- Project-level agents and a meta-agent co-evolve through feedback
- Suggestions are investigated before being surfaced, not just generated
- Today's briefing is tomorrow's input — the system accumulates institutional knowledge
- The loop converges: low-quality suggestions are eliminated, high-quality ones are deepened

### 2.2 Depth Through Specialization, Breadth Through Aggregation

No single agent tries to understand everything. Project agents go deep (read source code, check tests, understand architecture). The meta-agent goes broad (read summaries, find patterns, connect research). Recursion bridges the two: meta-insights flow down to project agents for feasibility evaluation, project-level findings flow up to the meta-agent for cross-cutting analysis.

### 2.3 Investigated Recommendations, Not Raw Suggestions

A suggestion like "consider sparse matrices" is noise. An investigated recommendation looks like: "Switch compute_cubical_ph to sparse_rips_complex — GUDHI supports this natively (docs section 4.3), estimated 60% memory reduction for grids >128x128, your February research notes on sparse Betti computation confirm the theoretical basis. Two test cases need updating: test_simple_block_single_component and test_ring_has_h1." The recursive architecture enables this depth.

### 2.4 The Vault Is the Shared State

All agents communicate through the Obsidian vault filesystem. No databases, no APIs between agents, no shared memory beyond files. This means:
- Any agent's output is human-readable markdown
- The system is fully transparent — you can read every intermediate analysis
- Debugging is trivial — read the files the agent read and wrote
- The vault is the single source of truth

### 2.5 Fractal Consistency

The same recursive pattern (specialized analysis → aggregation → feedback → refinement) applies at every scale: within a file, across a module, across a project, across all projects, across research domains. The architecture does not change at different scales — only the scope of what each agent reads.

## 3. Architecture

### 3.1 System Layers

```
LAYER 1: INGESTION (symlinks, not hooks)
Projects write session data to their own directories as normal.
Symlinks in the vault point to project-generated data.
Zero ingestion code. Zero hooks. Instant visibility.

LAYER 2: STORAGE
Obsidian vault with structured conventions.
Human-readable. Interlinked. Searchable.
The shared communication bus for all agents.
Symlinked data (project-generated) + vault-native data (agent-generated).

LAYER 3: ANALYSIS
Recursive multi-agent overnight loop.
Project agents (deep, parallel) + Meta-agent (broad, sequential).
Self-critique, investigation, convergence.

LAYER 4: OUTPUT
Morning briefing + per-project suggestion files.
Confidence-tiered. Evidence-backed. Feedback-enabled.
session-init hooks surface relevant suggestions at work start.

LAYER 5: FEEDBACK
Human ratings on suggestions feed back into the next cycle.
System learns which suggestion types are valuable.
Temporal tracking: suggestions have lifecycles (new → investigated → acted-on → closed).
```

### 3.3 Ingestion Layer (Detail)

Ingestion uses **symlinks, not hooks**. Projects write session data to their own `.claude/sessions/` directory during normal work. The vault sees this data instantly via symlinks. Zero ingestion code.

#### 3.3.0 Project Registration

One command registers a project with the system:

```bash
#!/bin/bash
# register-project.sh <project-name> <project-path>
PROJECT=$1
PATH_TO_PROJECT=$2
VAULT=~/vault/Projects/$PROJECT

mkdir -p "$VAULT/suggestions/active" "$VAULT/suggestions/implemented" "$VAULT/suggestions/rejected"

# Symlink project-generated data into vault (read-only from vault's perspective)
ln -s "$PATH_TO_PROJECT/.claude/sessions" "$VAULT/sessions"

# Create vault-native placeholders (written by agents, not symlinked)
touch "$VAULT/status.md" "$VAULT/analysis.md" "$VAULT/analysis-prev.md"
touch "$VAULT/decisions.md" "$VAULT/architecture.md"

echo "Registered $PROJECT. Vault sees sessions at $VAULT/sessions/"
```

**What's symlinked (→):** Data that originates in the project repo. Session summaries, task state. The project writes it during normal work. The vault sees it instantly.

**What's vault-native:** Data that originates from the overnight agents. Analysis, suggestions, decisions, architecture snapshots. Written directly into the vault. No symlink needed — they don't exist in the project.

This separation means: projects never need to know the vault exists. The vault aggregates. Agents analyze.

#### 3.3.4 Personal Journal

Manually written in `Journal/`. Daily entries may contain any combination of:
- Reflections on the day's work
- Questions about implementation approaches
- Future project ideas
- Frustrations or blockers (emotional signal, not just technical)
- Connections noticed between projects or research

**Trust class:** `config` (0.05/day decay). This means a journal entry retains useful trust for ~2 weeks before needing re-verification. This is appropriate because journal reflections represent thinking that evolves over days/weeks, not hours (ruling out `state` at 0.1/hour — that would zero out a morning entry by afternoon) and not months (ruling out `structural` at 0.01/week). Entries expressing permanent values ("I want to focus on TDA for my dissertation") should be manually tagged `trust_class: immutable` in frontmatter.

**Agent access:** Read-only. Agents NEVER write to `Journal/`. This is the user's private thinking space. Agents read it to understand priorities, questions, and emotional context — a journal entry saying "frustrated that persistent-homology's test suite is slow" should boost the priority of performance-related suggestions.

**How each agent uses the journal:**
- **Meta-agent:** Reads recent journal entries (last 7 days) to understand current priorities and questions. A journal entry asking "should I switch to sparse matrices?" means the sparse matrix suggestion gets HIGH confidence — the user is already thinking about it.
- **Weekly synthesis:** Incorporates journal themes into the weekly review. "This week you wrote about X three times — this seems to be a priority."
- **Investigation agent:** If the journal mentions a specific question ("how does GUDHI handle sparse filtrations?"), the investigation agent can research it proactively.

#### 3.3.5 Research Notes

Manually maintained in `Research/`. The system reads but does not write to this directory (human-curated knowledge). Obsidian's `[[wiki-links]]` and `#tags` provide the linking structure that agents traverse.

#### 3.3.6 Literature Library (Zotero Integration)

The user's Zotero library — papers read, annotated, and collected for dissertation research — is synced into the vault as markdown literature notes via the ZotLit Obsidian plugin.

**Sync pipeline (Obsidian-side, not agent-controlled):**

```
Zotero Library
  → Better BibTeX (auto-export .bib/.json on change)
  → ZotLit Obsidian plugin (creates/updates Literature/*.md)
  → Each literature note contains:
      - Metadata (title, authors, year, journal, DOI, tags)
      - Abstract
      - Annotations and highlights (imported from Zotero)
      - User notes (if any)
      - Citation key (e.g., @adams2017persistence)
```

**Example literature note** (`Literature/@adams2017persistence.md`):

```markdown
---
citekey: adams2017persistence
title: "Persistence Images: A Stable Vector Representation of Persistent Homology"
authors: [Henry Adams, Tegan Emerson, et al.]
year: 2017
journal: JMLR
doi: 10.5555/3122009.3242006
tags: [persistent-homology, vectorization, machine-learning, stability]
zotero_read: true
zotero_annotated: true
---

## Abstract
[auto-imported from Zotero]

## Annotations
[auto-imported highlights and margin notes from Zotero]

## Notes
[user's reading notes, if any]
```

**How agents use the literature library:**

| Agent | How it uses Literature/ |
|-------|----------------------|
| **Project agent** | Checks if the project's approach aligns with or contradicts cited papers. "src/discrimination.py implements persistence images — see [[Literature/@adams2017persistence]]" |
| **Meta-agent** | Finds literature that bridges projects. "This paper on Wasserstein stability applies to both persistent-homology and your reservoir modeling research." |
| **Investigation agent** | When investigating a suggestion, searches Literature/ for supporting or contradicting evidence. Cites specific papers in the recommendation. |
| **Investigation agent** | Detects **unread papers**: if a Zotero item has `zotero_read: false` and its tags match an active suggestion's topic, the briefing says "You have an unread paper directly relevant to this suggestion." |

**Paper discovery (investigation agent capability):**

When the investigation agent researches a suggestion and finds no relevant papers in the library, it can:
1. Search the web for relevant papers (via WebSearch)
2. Suggest specific papers to add to the Zotero library
3. Include the suggestion in the briefing: "No papers in your library cover sparse cubical complexes. Consider: [paper title] ([DOI link]) — cited 47 times, directly addresses this gap."

This is optional and only triggered for HIGH confidence suggestions where the investigation agent is doing deep research. The Zotero MCP (`zoty` — 8 tools, BM25 search) can also be used for direct library queries if the ZotLit literature notes aren't sufficient.

**The powerful loop:**

```
Project agent: "persistent-homology uses dense matrices — performance gap"
         ↓
Meta-agent: "Research/sparse-representations.md discusses alternatives"
         ↓
Investigation agent searches Literature/:
  → Found 3 papers tagged [persistent-homology, sparse] in library
  → 2 have zotero_read: false — user hasn't read them yet
  → Paper @obayashi2018volume specifically describes sparse cubical complexes
         ↓
Briefing:
  "Switch to sparse cubical complexes in compute_cubical_ph.
   Supporting literature (in your Zotero library, unread):
   - @obayashi2018volume: 'Volume-Optimal Cycle for Persistent Homology'
   - @kerber2017geometry: 'Geometry Helps to Compare Persistence Diagrams'
   Read @obayashi2018volume first — directly describes the sparse approach."
```

This connects overnight code analysis to the dissertation reading list. A suggestion about code becomes a reading assignment grounded in your own collected literature.

#### 3.3.7 Decision Records

A hybrid of auto-generated (from commit messages and session summaries) and manually written entries. Stored per-project. These are the highest-value data for the meta-agent — understanding WHY decisions were made enables challenging those decisions when new information emerges.

### 3.4 Analysis Layer (Detail)

The overnight analysis is a recursive multi-agent loop. Each cycle consists of phases that feed each other.

#### 3.4.1 Process State: Environment Variables

The orchestrator communicates ephemeral state to agents via environment variables, not files. This is faster than parsing state files and can't get stale.

```bash
# Set by the orchestrator before spawning each agent
export RIS_PHASE="analysis"        # or "meta", "refinement", "investigation", "compose"
export RIS_CYCLE="3"               # which recursive cycle
export RIS_PROJECT="persistent-homology"  # which project (for project agents)
export RIS_BUDGET="15"             # max tool uses for this agent (file reads, searches, etc.)
export RIS_VAULT="$HOME/vault"     # vault root path
```

**Where env vars beat files:**
- Current step/phase (ephemeral, changes per invocation)
- Cycle number (incremented by orchestrator, not persisted)
- Budget remaining (max tool uses — agent includes this in its system prompt as a self-imposed limit via `--max-turns` or equivalent)
- Agent identity ("am I the project agent or the meta agent?")

**Where files beat env vars:**
- Suggestion history (persists across days)
- Feedback patterns (accumulates over weeks)
- Session summaries (permanent record)
- Analysis results (consumed by next phase)

**The rule:** env vars for "where am I right now," files for "what have I learned."

### 3.7 Temporal Trust Layer

Context decays. A session summary from yesterday is near-certain; one from three weeks ago may describe code that's been refactored. A library version confirmed last month may have a newer release. An IP address from this morning may have changed. The system needs to distinguish fresh facts from stale ones — and know when to verify before acting.

#### 3.7.1 Trust Classes

Every piece of data in the vault has an implicit or explicit trust class that determines how quickly its reliability decays:

| Class | Decay rate | Examples | Verify? |
|-------|-----------|----------|---------|
| **immutable** | 0/ever | User rules ("never delete repos"), permissions, core principles | Never |
| **structural** | 0.01/week | Repo structure, file locations, CLAUDE.md content, architecture.md | Monthly |
| **infrastructure** | 0.02/day | IPs, ports, hostnames, DNS entries, server configs | On use if >3 days old |
| **config** | 0.05/day | Service configs, API keys, dependency versions | On use if >1 day old |
| **state** | 0.1/hour | Task progress, build status, test results, deployment state | Always verify |
| **ephemeral** | 0.5/hour | "Build is passing", "server is reachable", "training at step N" | Never trust, always check |

#### 3.7.2 Trust Calculation

```
current_trust = initial_trust × (1 - decay_rate × age)
```

Where `age` is measured in the decay rate's unit (hours, days, weeks). Clamped to [0.0, 1.0].

**Agent behavior by trust level:**

| Trust range | Agent behavior |
|-------------|---------------|
| 0.8 - 1.0 | Act on it directly |
| 0.5 - 0.8 | Act on it, but note the age in the briefing |
| 0.2 - 0.5 | Verify before acting (run `verify_command` if available) |
| 0.0 - 0.2 | Treat as "probably wrong" — verify before even mentioning |
| 0.0 | Ignore unless explicitly asked |

#### 3.7.3 Verify Commands

The key feature: instead of just decaying trust and hoping, agents can actively verify. Each context entry can optionally include a verify command:

```yaml
# Meta/temporal-trust.yaml (examples)
entries:
  - fact: "GUDHI 3.9.0 added sparse_rips_complex documentation"
    source: investigation-agent
    written: 2026-03-24
    trust_class: config         # library versions change slowly
    verify_command: "pip show gudhi | grep Version"

  - fact: "persistent-homology has 101 tests passing"
    source: project-agent
    written: 2026-03-24
    trust_class: state          # test counts change with every session
    verify_command: "cd ~/projects/persistent-homology && python -m pytest --co -q 2>/dev/null | tail -1"

  - fact: "Do not delete git repos"
    source: user-rule
    written: 2026-01-01
    trust_class: immutable
    verify_command: null         # rules are not verified, they are obeyed
```

Verification is cheap compared to acting on wrong data. A `pip show`, `git log -1`, or `pytest --co -q` takes milliseconds and prevents wasted analysis time.

#### 3.7.4 Tiered Verification Depth

Shallow verification often lies. `ping` succeeds but the service is down (container up, Java not started). `curl` returns HTTP 200 from the auth page but the API behind it is broken. A reverse proxy masks the real service state. Verification must match the depth needed:

```yaml
# Verification tiers per trust class
verify_shallow: "pip show gudhi | grep Version"           # package exists?
verify_deep:    "python -c 'from gudhi import CubicalComplex; print(\"ok\")'"  # import works?
verify_full:    "cd ~/projects/persistent-homology && python -m pytest tests/test_persistence.py -x -q"  # actually runs?
```

| Trust class | Default verify depth | Rationale |
|-------------|---------------------|-----------|
| immutable | none | Rules are not verified, they are obeyed |
| structural | shallow | File existence, package version — rarely wrong |
| infrastructure | deep | Check the actual service, not just the host |
| config | deep | Verify the config loads, not just that the file exists |
| state | shallow | Quick check, but treat ambiguity as stale |
| ephemeral | none or shallow | Not worth deep verification — just re-check the source |

**Ambiguity fallback hierarchy:**

```
verify succeeds clearly    → trust the data, log the check
verify fails clearly       → mark STALE, run deeper check if available
verify is ambiguous        → depends on trust_class:
  infrastructure → escalate to verify_deep or verify_full
  config         → ASK the user (ambiguous config is dangerous)
  state          → treat as stale (cheap to re-check the source)
  ephemeral      → treat as stale (never worth investigating)
```

**The principle:** verification depth should match trust class. The cost of verification should never exceed the cost of acting on wrong data. Ephemeral data gets a quick check or nothing. Infrastructure gets SSH + service check. Immutable gets nothing.

**Real-world lesson (from production multi-agent systems):** The most common verification failure is multi-layer ambiguity — the check validates one layer (host is up) but misses another (service behind reverse proxy is down). For the overnight intelligence system, this primarily affects investigation agents checking library versions or API availability. The mitigation: verify_deep for investigation agent checks should test the actual import/function call, not just the package existence.

#### 3.7.5 How Each Agent Uses Temporal Trust

| Agent | How it uses trust |
|-------|------------------|
| **Project agent** | When reading `sessions/`, weight recent sessions higher. A finding from yesterday matters more than one from 2 weeks ago. Flag stale architectural claims. |
| **Meta-agent** | Recognize that feedback patterns can drift. A preference from month 1 may not apply in month 3. Cross-project suggestions based on old data should be re-verified. |
| **Investigation agent** | When citing library versions or API docs, check information age. "GUDHI 3.9.0 released Feb 2026" has high trust in March but should be re-verified by June. Run verify_commands where available. |
| **Refinement agent** | Downgrade confidence on suggestions whose evidence is aging. A suggestion based on a 3-week-old session summary should score lower than one based on yesterday's. |
| **Briefing composer** | Include trust metadata in the briefing so the human knows which recommendations are based on fresh vs stale data. |

#### 3.7.6 Suggestion Trust Decay

Suggestions themselves decay. A suggestion sitting in `active/` for 30 days already gets auto-archived (binary threshold in the current design). Temporal trust replaces this with a continuous curve:

- Day 1: suggestion trust = 1.0 (just investigated)
- Day 7: trust = 0.85 (still relevant, code may have changed)
- Day 14: trust = 0.65 (code has likely changed; re-investigate before acting)
- Day 30: trust = 0.35 (probably stale; auto-archive or re-investigate)

If a suggestion is re-investigated and confirmed, its trust resets to 1.0. If it's contradicted by new evidence, it's closed. This replaces the binary 30-day archive with a curve that naturally prioritizes fresh, re-verified suggestions.

#### 3.7.7 Implementation

Temporal trust is stored as frontmatter on vault files and as entries in `Meta/temporal-trust.yaml`:

- **Frontmatter** (per-file): suggestions, analysis results, and session summaries include `written:` and `trust_class:` in their YAML header. Agents read this when loading context.
- **temporal-trust.yaml** (system-wide): explicit high-value facts with verify commands. The orchestrator loads this at the start of each nightly run and passes trust-filtered context to agents.
- **Trust calculation** runs at load time, not at write time. No cron job needed to update trust scores — they're computed from `written` + `decay_rate` + `current_time` when the agent reads the entry.

#### 3.7.8 Decay Rate Self-Calibration

The initial decay rates (section 3.7.1) are first-pass estimates. The system self-calibrates using the same feedback loop pattern as suggestion lifecycle ratings:

```
verify_ran → data_was_stale → increase decay_rate for this trust_class
verify_ran → data_was_fresh → decrease decay_rate (or widen verify interval)
```

Tracked in `Meta/temporal-trust.yaml` per trust class:

```yaml
calibration:
  infrastructure:
    verify_count: 47
    stale_count: 3
    stale_rate: 0.064        # 6.4% of verifications found stale data
    current_decay: 0.02/day  # initial default, seems appropriate
    adjustment: none          # stale_rate < 10%, decay is well-calibrated

  state:
    verify_count: 112
    stale_count: 61
    stale_rate: 0.545        # 54.5% stale — decay rate too low
    current_decay: 0.1/hour
    adjustment: increase to 0.2/hour  # data changes faster than modeled
```

The orchestrator reviews calibration data monthly and adjusts decay rates. This is a slow outer loop — decay rates are stable properties of information classes, not per-entry tuning.

This is a standalone module. Any project using the template could opt into temporal trust independently of the full recursive intelligence system.

## 4. Agent Prompts (Specifications)

Each agent is defined by a prompt file in `Meta/agent-prompts/`. These are the system prompts that drive agent behavior. They are stored in the vault so they can be iterated on and version-controlled.

### 4.0 Prompt Development Workflow

**Do NOT iterate prompts via the overnight cycle.** The overnight cycle is for discovery ("what should I work on?"). Prompt iteration needs a fast inner loop:

1. Save yesterday's vault state as a snapshot (copy or git stash)
2. Run the agent against the snapshot with the current prompt
3. Read results — qualitative analysis of failures
4. Adjust the prompt
5. Re-run immediately against the same snapshot
6. Compare output quality
7. Repeat until satisfied

Expected: **3-5 iterations to reach 50% useful output**, achievable in a single afternoon. The key: test against real session data from your vault, not synthetic examples. The vault already has this data.

This is the same pattern as eval-driven development (EDD): define what "good" looks like, measure, iterate. The overnight cycle validates in production; the snapshot loop iterates in development.

```
2. Report which suggestions were acted on and their outcomes
3. Identify recurring themes across daily briefings (same suggestion surfacing repeatedly = high priority)
4. Assess goal alignment: is active work moving toward stated objectives?
5. Propose priorities for next week based on active suggestions + project state
6. Note any journal themes that appeared multiple times

Output: Briefings/weekly/YYYY-WNN.md
Tone: reflective but actionable. This shapes the next week's work.
```

### 4.7 Monthly Synthesis Prompt (Summary)

```
You are the monthly synthesis agent. You run on the 1st of each month at 6 AM.

Your inputs:
- Briefings/weekly/ from the past 4-5 weeks
- Meta/suggestion-lifecycle.md (full history)
- Meta/feedback-patterns.md
- Meta/convergence-log.md (system health)
- Previous monthly synthesis (if exists)

Your job:
1. Month-over-month progress per project
2. Suggestion quality metrics: what % of HIGH suggestions were rated useful?
3. System health: convergence speed, investigation accuracy, decay calibration
4. Strategic recommendations: what should change about priorities or approach?
5. Literature integration: any papers read this month that changed understanding?
6. Flag drift: are any projects stalling? Any goals being neglected?

Output: Briefings/monthly/YYYY-MM.md
Tone: strategic. This is the highest-level view of the portfolio.
```

**Scheduling for weekly and monthly agents:**

The orchestrator runs three cron jobs:

| Agent | Cron expression | Trigger |
|-------|----------------|---------|
| Nightly analysis loop | `30 5 * * *` | Every day at 5:30 AM |
| Weekly synthesis | `0 6 * * 0` | Sundays at 6:00 AM (after nightly completes) |
| Monthly synthesis | `0 6 1 * *` | 1st of month at 6:00 AM |

Weekly and monthly agents are standalone — they read accumulated vault state, not live analysis output. They do NOT participate in the recursive convergence loop.

### 6.4 System Health Metrics

Tracked in `Meta/convergence-log.md`:

| Metric | Healthy range | Action if unhealthy |
|--------|--------------|---------------------|
| Convergence cycles per run | 2-4 | >5: agents are oscillating, review prompts |
| Suggestions per briefing | 3-8 | >12: noise, tighten confidence thresholds. <2: too conservative |
| User action rate | >40% of HIGH suggestions | <20%: suggestions aren't useful, review analysis dimensions |
| Investigation accuracy | >70% of investigated suggestions rated useful | <50%: investigation prompts need tuning |
| Cycle wall-clock time | 15-45 min | >90 min: too many investigations, tighten selection |

## 7. Security and Safety

### 7.1 Read-Only Source Access

All agents have READ-ONLY access to project source code. No agent writes to any project repository. The vault is the ONLY filesystem the agents modify. This means:
- An overnight agent cannot introduce bugs
- An overnight agent cannot make commits
- An overnight agent cannot modify tests
- The worst case is a bad suggestion in the vault (easily ignored or deleted)

### 7.2 Vault Isolation

The vault is a separate directory from any project. Agents cannot escape the vault boundary. mcpvault's configuration restricts access to the vault path only.

### 7.3 Symlink Safety

The vault uses symlinks for ingestion (project sessions/ and status.md). Specific risks and mitigations:

| Risk | Mitigation |
|------|-----------|
| **Circular symlinks** | Vault → project → vault loops. Claude's tools have depth limits, but overnight agents need explicit guards. register-project.sh must validate no cycles. |
| **Dangling symlinks** | Deleted project leaves broken links. Orchestrator checks symlink targets exist before spawning project agents; skip with warning if dangling. |
| **Git confusion** | Symlinks in a git repo store the link path, not content. Cloning on another machine breaks links. Fix: `.gitignore` all symlinked directories, only commit vault-native content. |
| **Path confusion** | Claude may reference a file as `vault/Projects/foo/sessions/file.md` when the real path is `~/projects/foo/.claude/sessions/file.md`. Fix: document symlinks in vault CLAUDE.md so agents understand the mapping. |
| **Write-through** | An agent writing to a symlinked path modifies the project repo. Fix: agents ONLY write to vault-native paths (analysis.md, suggestions/, briefings/). Symlinked paths are read-only by convention. Orchestrator should validate this. |

**Why symlinks, not hardlinks:** Projects and vault may be on different filesystems (or will be eventually). Hardlinks can't cross filesystem boundaries. Git stores hardlinks as independent copies, defeating the purpose. Symlinks are the right tool.

### 7.4 Cost Guardrails

- Max 5 recursive cycles per nightly run
- Max 2 hours total wall-clock time
- Max 3 investigation agents per cycle (most expensive operation)
- Convergence check prevents infinite loops
- All costs are within Claude Max subscription (no per-token billing)

### 7.5 No Autonomous Code Changes (v1)

The system suggests and investigates but does NOT implement. This is intentional:
- Suggestions must be reviewed by a human before code changes
- The feedback loop requires human judgment to train the system
- Autonomous implementation (Level 4 action recursion) is a future evolution gated on demonstrated suggestion quality

## 9. Open Questions

| 6 | Agent model selection | Sonnet for project/refinement/composer agents (narrow, don't overthink). Opus for meta-agent and investigation (reasoning depth). Via `RIS_MODEL` env var per phase. Cheap models are often BETTER for narrow tasks. |
| — | Convergence threshold | Start at delta < 0.05 (5%), calibrate empirically. Convergence is non-monotonic: cycle 2 often overcorrects before cycle 3 recovers. Check delta against N-2 as well as N-1 to detect oscillation. |
| — | Prompt iteration | Fast inner loop against vault snapshot (3-5 iterations to 50% useful, one afternoon). Do NOT iterate via overnight cycle. Test against real session data. |
| — | Decay rate calibration | First-pass defaults are reasonable. Self-calibrate from verify_command hit rate (same feedback pattern as suggestion ratings). Monthly review by orchestrator. |
| — | Verify command reliability | Shallow verification often lies (ping succeeds but service is down, auth page returns 200 but API is broken). Use tiered depth: shallow → deep → full. Ambiguity fallback depends on trust class: infrastructure escalates to deeper check, ephemeral treats as stale, config asks the user. |

## 10. Architectural Lineage

This design shares structural DNA with several existing systems:

| This system | Parallel | Shared pattern |
|-------------|----------|---------------|
| Project agents (deep, parallel) | Observer bots in multi-agent systems | Specialized, parallel, scope-limited |
| Meta-agent (broad, sequential) | Orchestrator pattern | Reads summaries, finds cross-cutting patterns |
| Convergence loop | Bounded recursion | Iterate until stable, with max-cycle safety |
| Vault as shared state | Shared world state in multi-agent architectures | All agents read from one state, specific agents write to designated areas |
| Symlink ingestion | Zero-copy shared memory | Data stays where it's produced, consumers see it without transfer |

The recursive multi-agent pattern (specialized observers → cross-cutting orchestrator → convergence) appears independently in several domains. This design applies it to cross-project software intelligence.
